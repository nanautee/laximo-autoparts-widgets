# Архитектура

```
Browser (shop page or demo)
   │  fetch, JSON only
   ▼
Frontend widgets  ──►  window.AutopartsWidgets (embed API)
   │
   ▼  same-origin (or VITE_API_BASE)
Backend (Spring WebFlux)
   ├─ controller  ── валидация, HTTP-коды, meta
   ├─ service     ── оркестрация, CacheStatus
   ├─ JsonCacheService ── Redis, namespace + TTL
   └─ client
        ├─ LaximoGateway  ── SOAP (live) | MockLaximoGateway (demo)
        └─ AbcpCartClient ── HTTP (live) | simulated (demo)
```

## Почему WebFlux

Виджет делает несколько независимых запросов (VIN, корень дерева, OEM), а ответы
Laximo и ABCP — сетевые вызовы. Реактивный стек позволяет не блокировать поток
на каждом I/O и удерживать десятки параллельных сессий на одном инстансе.

## Слои backend

**`controller`** — только транспорт: разбор параметров, делегирование, сборка
`X-Cache` / `X-Source` заголовков. Бизнес-логики нет.

**`service`** — сценарии (`VehicleService`, `CatalogService`, `OemService`,
`CartService`). Каждый метод возвращает `Mono<ServiceResult<T>>`, где
`ServiceResult` несёт данные вместе с `ResponseMeta` (source, cache, tookMs).
Так виджеты получают единый формат ответа на всех endpoint'ах, а статистика
кэша не теряется по дороге.

**`JsonCacheService`** — единственное место, где решается, можно ли переиспользовать
ответ. Логика: прочитать из Redis → при промахе вызвать loader, записать с TTL →
при ошибке Redis пройти мимо кэша со статусом `BYPASS`.

Два решения здесь стоит назвать явно:

1. **Значения сериализуются через `TypeReference`**, а не через `List.class`.
   При `List.class` Jackson теряет тип элемента и дерево каталога
   десериализуется в список `Map` — первый же `node.kind()` упал бы с
   `ClassCastException`. Типы вынесены в `CacheTypes`.
2. **Ключи хэшируются** (SHA-256, 12 байт). Цепочки вида `group:X|vehicleId`
   не упираются в лимиты Redis, и VIN не лежит в ключе открытым текстом.

**`client`** — адаптеры внешних систем. `LaximoGateway` — интерфейс с двумя
реализациями: `LaximoSoapClient` для боевого режима и `MockLaximoGateway` для
демо. Выбор делает `AutopartsGatewayConfig` по `MOCK_ENABLED`, поэтому
остальной код не знает, откуда пришли данные, — а `meta.source` честно
показывает источник в ответе.

Разбор XML сделан через `Xml` с поиском по локальному имени и tolerant
поведением: WSDL Laximo различается между рынками и версиями сервиса, и
отсутствующий узел должен давать `null`, а не исключение.

## Фронтенд

Никаких фреймворков и рантайм-зависимостей: виджеты должны вставляться в
любую страницу магазина одним `<script>`.

- `core/api.ts` — типизированная обёртка над `fetch`. Единственное место,
  которое знает про HTTP.
- `core/cart-store.ts` — наблюдаемое состояние корзины (подписки, без
  фреймворка). Общее для всех экземпляров виджетов на странице.
- `core/parts-tree.ts` — ленивое дерево деталей: уровень подгружается при
  раскрытии группы, кэш уровней живёт в инстансе виджета.
- `embed.ts` — публичный API: `mount`, `mountAll`, `addToCart`, `cartStore`.
  CSS инжектится автоматически, поэтому странице магазина не нужно ничего
  подключать.

Адрес backend резолвится **на каждый запрос** (`getApiBaseUrl()`), а не один
раз при загрузке модуля: страница магазина задаёт
`window.__AUTOPARTS_CONFIG__.apiBase` уже после того, как бандл выполнился.

## Сквозные решения

| Решение | Причина |
|---|---|
| Единый конверт `{ data, meta }` | фронтенд не различает endpoint'ы по формату ответа |
| `meta.cache` + `X-Cache` | поведение кэша проверяемо в Swagger и UI |
| Redis как optional | деградация до `BYPASS` вместо отказа виджета |
| `MOCK_ENABLED` вместо заглушек в коде | demo и live — один и тот же путь кода |
| Нет ключей в репозитории | доступы только через переменные окружения |
